Hermesをorchestratorの中心に置き、Orcaでエージェントとworktreeを調整し、wtxでworktreeごとのruntimeを分離する開発ワークフロー。

control plane task DAG runtime isolation barrier first

設計の一行要約

Hermes は「何を、どの順で、どの条件なら進めるか」を決める。
Orca は「誰が、どのworktreeで動いているか」を持つ。
wtx は「そのworktreeのサービス環境」を用意する。

01 / architecture

3つの層に、3つの責務。

境界を混ぜないことが、並列開発を安定させる。Hermes・Orca・wtxは、同じ「開発を自動化する道具」でも管理する状態が異なる。

THE OPERATING PRINCIPLE

Hermesが直接すべてを触るのではなく、各層の状態をその層のAPIで更新する。

  1. タスクとworktreeはOrcaに作らせる
  2. runtimeの準備はwtxに委譲する
  3. 判断と例外処理はHermesに戻す
02 / standard flow

標準フローは、
barrierを中心に組む。

worktreeが作られたことと、runtimeが使えることは別の状態。agentの開始は、wtxのready receiptを受け取った後にだけ許可する。

要求を、実行可能な単位にする。

Hermesはユーザーの要求をそのままagentへ投げず、対象リポジトリの規約・依存関係・受け入れ条件を先に確認する。

  • 変更対象と変更しない範囲を決める
  • 必要なサービス、DB、Simulatorを特定する
  • 完了条件をテスト可能な言葉にする
roleHermes
outputtask brief + acceptance criteria
next gateDAGへ分解できるか

依存関係を、DAGとして見える化する。

独立して進められる作業と、前段の成果物が必要な作業を分ける。並列化は「同時にできるか」ではなく「同じ状態を触らないか」で判断する。

  • design → API / frontend / testsの依存を定義
  • merge前に必要なreviewを後段へ置く
  • 曖昧な仕様は作業開始前にescalateする
roleHermes
outputtask DAG + dispatch plan
next gate依存のないtaskから開始

Orcaにworktreeと実行単位を持たせる。

各taskは専用worktreeとagent terminalに割り当てる。Hermesが覚えておくのは目的と制約、Orcaが持つのは実際の実行状態。

  • parallel taskは別worktreeにする
  • agent間のやり取りはOrcaのthread / task状態へ残す
  • 完了・block・escalationを明示的な状態にする
roleOrca
outputworktree path + agent terminal
next gatewtx ready receipt

agentを起動する前に、runtimeを保証する。

Orcaがworktreeを作っただけでは、DBやDockerが使えるとは限らない。wtxの冪等なensureをbarrierとして扱い、readyになるまでagentを起動しない。

  • wtx ensure ... --jsonの成功を待つ
  • 必要なserviceをwtx execで起動する
  • 失敗時はtaskをblockし、host Dockerへfallbackしない
rolewtx
outputschema_version付きready receipt
next gateagent startupを許可

編集はhost、runtime依存の検証はVMへ。

coding agent、editor、Git、GitHub操作はhostで行う。Docker、DB、service、container依存testだけをwtxへ送る。

  • agentは通常のworktreeファイルを編集する
  • wtx exec -- docker compose ...でサービスを操作する
  • 完了報告には変更・テスト・未検証リスクを含める
rolecoding agent
outputcommit + structured result
next gateworker_done / escalation

レビュー結果をHermesが統合判断する。

実装完了は統合可能と同義ではない。Orcaでreview gateを開き、Hermesが指摘・テスト・リスクを比較して次のtaskを解除する。

  • correctness / security / test観点を分けてreviewする
  • 重大指摘は実装taskへ戻す
  • runtime cleanup成功後にworktreeを閉じる

next gate統合またはユーザー確認

03 / runtime contract

wtxは、runtimeだけを持つ。

Orcaが作ったworktreeの絶対パスをjoin keyにして、wtxがVMとruntime readinessを返す。taskの進捗やagentの状態をwtxに持ち込まない。

01 / readiness barrier
# worktree作成後、agent起動前に実行
wtx ensure "$ORCA_WORKTREE_PATH" \
  --json
02 / service startup
# container依存のcommandだけVMへ
wtx exec -- docker compose \
  up -d --wait
wtx port add api:3000
wtx env
03 / inspect
# readiness / branch / portを機械的に確認
wtx inspect "$WTX_VM_NAME" \
  --json
# stdout: JSON / stderr: warning
04 / cleanup order
# runtimeを先に消してからworktreeを閉じる
wtx rm "$WTX_VM_NAME" \
  --if-exists --json
# success後にOrca側でworktreeをarchive

コマンドの正確な引数は実行中のbinaryのhelpを優先。詳細は Orchestrator contract と CLI reference を参照。

ORCHESTRATOR

taskとworktree

Orca / Hermesが所有。依存関係、agent terminal、完了状態、review gateを扱う。

JOIN KEY

正規化済み絶対パス

Orcaが作ったworktreeと、wtxが準備するVMを結びつける不変の参照。

RUNTIME PROVIDER

VMとサービス

wtxが所有。dockerd、DB、volume、port、Simulator、readinessを扱う。

04 / patterns

この構成から広げられる3つの型。

最初はFeature DAGから始め、原因調査とレビューを分離する。runtimeが分かれることで、並列作業の失敗を比較可能にできる。

PATTERN 01

Feature DAG

API、frontend、migration、testsを依存関係付きで並列化する通常形。

design→API+web→review
PATTERN 02

Bug matrix

同じ再現手順を複数のwtx VMで実行し、発生条件を比較してから修正する。

repro→VM A+VM B→cause
PATTERN 03

Review tournament

correctness、security、testを別のreviewerに分担し、Hermesが判断を集約する。

code→3 reviews→gate
05 / guardrails

自動化するほど、
ルールは少なく強く。

このワークフローで守るべき不変条件。特に「準備失敗時に別runtimeへ逃がさない」が重要。

01
agentはready receiptの後に起動

worktree.createdのeventだけを信頼せず、wtx ensureの成功をbarrierにする。

02
host Dockerへsilent fallbackしない

wtxが失敗したらtaskをblockし、別の共有runtimeで続行しない。

03
agentとGitはhost、serviceはVM

標準形ではcredentialsもhostに置き、VM内agentへの共有は明示的なopt-inにする。

04
cleanupはruntimeが先

wtx rmの成功を確認してから、Orca側のworktreeを閉じる。

05
parallel taskは別worktree

同じファイルと同じGit refを複数agentが同時に編集しない。

06
wtxをsecurity sandboxと誤認しない

sourceと.gitはhost-visible。信頼できないcodeの封じ込め用途ではない。

06 / lifecycle

一つのtaskの、始まりから終わりまで。

担当層を追うと、どこで止まり、どこへ戻すべきかが見える。

01Hermes / plan
要求をtask briefへ変換。 受け入れ条件と依存関係を確定する。
02Orca / dispatch
worktreeとagent terminalを作成。 実行単位をOrcaの状態に登録する。
03wtx / ensure
専用VMとdockerdをreadyにする。 receiptを返すまでagentを待たせる。
04agent / implement
hostで編集し、VMでサービス依存テスト。 変更と検証結果を報告する。
05Hermes / decide
review結果を統合。 merge、reopen、block、ユーザー確認のいずれかを選ぶ。
06wtx → Orca / cleanup
runtimeを削除してからworktreeを閉じる。 失敗したらworktreeを残して再試行する。

Hermesが決め、Orcaが追跡し、wtxが隔離する。

この3者の責務を分けることで、複数のcoding agentを走らせても、taskの状態・Gitの作業場所・runtimeの状態を混ぜずに管理できる。
